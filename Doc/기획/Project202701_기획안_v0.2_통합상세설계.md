**부제:** 에이전트리스 OS·소프트웨어 인벤토리 및 취약점 영향 조사 시스템  
**기준일:** 2026-11-20  |  **문서 상태:** 검토·승인 전 통합 개선안  
**원본:** `Project202701_기획안_v0.1.pptx`(15장, 2026-11-20)  
**목적:** v0.1의 확정 원칙을 보존하면서 벤치마킹과 설계 검토 개선점을 누락 없이 구현 가능한 요구사항으로 구체화한다.

> **중요—결정 상태:** 아래의 **[원안 확정]**은 v0.1에서 확정된 기획 원칙이다. **[개선 권고]**는 본 문서가 새로 제안하는 설계로, 채택 전 검토가 필요하다. **[미결정]**은 관계자 승인 없이는 확정하지 않는다. 수치가 포함된 성능·보안 한도는 별도 표시가 없다면 **PoC 검증용 목표 초안**이다. 본 문서는 구현·승인을 대신하지 않는다.

## 0. 한눈에 보는 결론과 변경 통제

- **사업 목표는 불변:** 시스템을 한 번 등록하고 SSH(Windows는 추후 WinRM)로 OS·소프트웨어 버전을 주기적으로 수집한다. 보안 이슈 발생 시 조건 검색으로 영향 자산을 찾고, 최종 취약 여부는 관리자가 판단·기록한다. [원안 2, 4, 6쪽]
- **지켜야 할 네 가지 원칙은 불변:** ① 대상에 상주 에이전트를 설치하지 않음 ② SSH 개인키는 수집기에만 둠 ③ 웹에서 임의 명령을 전송·실행하지 않음 ④ 웹·수집기는 직접 연결하지 않고 DB 작업 테이블로 교환. [원안 3쪽]
- **유지할 확정 정책:** 내부망 전용 웹, 수집 전용 계정·키·IP 제한, 별도 수집기, 규칙 기반 탐지 확장, 관리자의 수동 취약 판단, 초기 수십 대→수백 대 확장. [원안 2~5쪽]
- **보강해야 할 설계:** 설치 인스턴스/탐지 증거 분리, 패키지 형식별 버전 비교, 미발견과 확인 불가 구분, 외부 노출 증거 관리, 승인형 규칙·자원 한도, 복구 가능한 작업 큐, 수집 신선도·운영 지표, 검증 기준. [개선 권고]
- **범위 확대 금지:** 취약점 DB 자체 운영, 자동 패치, 상시 에이전트, 전사 CMDB 대체, 모든 제품의 100% 탐지는 본 사업의 필수 범위가 아니다. [원안 취지 유지·구체화]
- **변경관리:** 구현 요구사항은 ID로 추적한다. 원안 확정 원칙을 바꾸려면 별도 변경요청서에 사유·영향·보안 승인·대체안을 남긴다. 미결정은 회의에서 결정일·결정자 기록 후 베이스라인을 갱신한다.

## 1. 배경·목표·성공 정의

### 1.1 현행 문제와 사용자 가치

현재 서버별 OS·Tomcat·Node.js 등의 버전을 사람이 조사·입력하므로 정보가 빠르게 오래되고 신규 보안 이슈의 전수 조사에 시간이 든다. 자동 인벤토리로 최신성을 높이고, **설치/실행/네트워크 노출**의 차이를 보여 보안 담당자의 조사·조치 우선순위 결정을 지원한다. 관리자/담당자가 사용하는 웹은 내부망에서만 접근한다. [원안 2쪽]

### 1.2 사업 목표 및 핵심 산출물

| ID | 목표 | 운영 산출물 |
|---|---|---|
| OBJ-01 | 한 번 등록 후 주기적 자동 수집 | 자산 마스터, 수집 일정, 최신 결과 |
| OBJ-02 | 신규 보안 이슈의 전체 영향 조사 단축 | 조건 검색, 탐지 증거, 내보내기 |
| OBJ-03 | 취약 판단의 근거 보존 | 이슈·판단자·상태·근거·일시·조치 이력 |
| OBJ-04 | 에이전트 미설치·최소 권한 운영 | 서버 최초 설정 절차, SSH/WinRM 권한 매트릭스 |
| OBJ-05 | 수십 대에서 500대급으로 확장 가능한 운영 | 동시성, 재시도, 실패 격리, 모니터링, PoC 부하 검증 |

### 1.3 범위와 경계

- **대상:** 내부 전용 서버 및 외부에서 접근 가능한 서버, 단계적으로 Windows와 네트워크 장비 포함. 자산 등록은 초기에는 웹 수동 등록과 엑셀 일괄 등록을 기본으로 한다. **기존 자산 목록과의 연동은 원안에서 '새로 등록'으로 합의된 상태이므로 임의로 필수화하지 않는다.** [원안 2, 6, 14쪽]
- **제공:** 수집·버전 검색·변경 이력·실패 진단·관리자 판단 및 후속 조치 상태 추적. 선택적 외부 위협 정보 반입은 후속 단계이며 자동 판정의 필수 구성요소가 아니다.
- **비범위:** 에이전트 배포·자동 보안 패치·네트워크 침투 테스트·취약점 자체 판정 엔진·완전한 EDR/SIEM/CMDB. 파일 내용의 과도한 수집이나 비밀번호·비밀키 추출은 금지.
- **지원 수준:** 모든 수집 대상 항목은 단계/OS별 `지원`, `제한 지원`, `향후`, `지원 불가`를 문서화한다. 탐지 기능 추가가 지원 보장을 의미하지 않는다.

## 2. 변경해서는 안 되는 핵심 원칙과 기본 아키텍처

### 2.1 v0.1 확정 사항 계승

| ID | 원칙/결정 [원안 확정] | 구현 시 지킬 조건 |
|---|---|---|
| BL-01 | Linux SSH 에이전트리스, Windows는 WinRM | 대상에 상주 수집 프로그램 설치 금지; 일반 명령/기본 기능 중심 |
| BL-02 | SSH 개인키는 수집기 내 파일에만 보관 | 웹 서버·브라우저·작업 DB·로그에 개인키/자격증명 금지; 0600 및 디스크 암호화 |
| BL-03 | 전용 계정·공개키, `authorized_keys`의 `from=` 제한 | 고정 출발지 IP 및 포워딩·PTY 제한; 최초 설정 담당자 수행 |
| BL-04 | 웹·수집기 별도 서버 | 웹↔수집기 직접 네트워크 차단; 대상 서버 접속은 수집기만 수행 |
| BL-05 | DB 작업 테이블로만 상호작용 | 웹은 명령 아닌 자산 ID·작업 유형·승인 규칙 참조만 등록 |
| BL-06 | 웹 양식으로 탐지 규칙 관리, 수집기 고정 엔진이 해석 | 허용 경로/엔진 기능 변경은 수집기 측 코드·배포 통제 |
| BL-07 | 취약 여부는 관리자가 최종 판단 | 자동 수집과 후보 검색은 제공하되 자체 CVE 데이터 소스 필수 운영 없음 |

**정확한 보안 해석:** DB 간접 연동은 웹 공격자가 수집기 포트에 직접 접근하는 위험을 줄이지만, DB의 악성 규칙/작업 입력을 통한 *간접 위험*까지 없애지는 않는다. 또한 `from=`·`no-pty`만으로 원격 명령 실행 자체가 차단되는 것은 아니다. 수집기 정책·접근 제어·승인·계정 최소 권한의 다층 방어가 필요하다. [S-06, S-07]

### 2.2 구성 및 통신 경계

1. **관리자 브라우저(내부망)** → **웹/API 서버**: 자산·규칙 등록, 승인, 검색, 결과 내보내기, MFA/RBAC.
2. **웹/API 서버** → **PostgreSQL(후보)**: 제한된 자산·규칙·작업 등록 및 결과 조회. 웹 DB 계정은 수집 결과/작업 상태를 직접 수정하지 못한다.
3. **수집기** ↔ **DB**: 승인된 작업 조회, 실행 상태/heartbeat 기록, JSON 스키마를 통과한 결과 저장. 수집기는 웹 서비스와 직접 연결하지 않는다.
4. **수집기** → **Linux/Unix(SSH)**: 등록한 호스트 키로만 인증하고 허용된 읽기 동작 수행. 키 그룹은 내부 전용/외부 노출 시스템 구분.
5. **확장 단계** 수집기 → **Windows(WinRM)** 또는 **네트워크 장비(SSH `show version`)**: 별도 어댑터와 자격증명 정책을 사용한다. 다른 프로토콜 추가는 별도 변경 승인 사항이다.
6. 방화벽 정책은 수집기→대상 방향만 기본 허용하고, 웹→대상 및 웹→수집기 연결은 금지한다. DB 연결은 업무 역할별 최소 허용한다.

## 3. 역할·권한·업무 시나리오

### 3.1 역할 정의 [개선 권고; 최종 권한은 미결정]

| 역할 | 허용 기능 | 명시적 금지 |
|---|---|---|
| 시스템 관리자 | 인프라·수집기 배포, 정책 한도, 키 교체 | 개인키를 웹에 등록하거나 규칙 승인 우회 |
| 자산 관리자 | 자산 생성/수정·엑셀 등록·수집 요청 | 엔진의 허용 명령·경로 정책 변경 |
| 규칙 작성자 | 탐지 규칙 초안 작성·시험 요청 | 본인 단독으로 운영 전체 적용 승인 |
| 규칙 승인자 | 시험 증거 검토·승인·롤백 | 승인하지 않은 원격 명령 허용 |
| 보안 분석자 | 이슈 등록·영향 후보 검색·판단/조치 추적 | 수집 자격증명 조회 |
| 조회 담당자/감사자 | 지정 자산 범위 조회·보고서·감사 기록 | 규칙 수정, 임의 실행, 판단 변경 |

- 최소 권한·역할별 조회 범위·권한 분리·MFA 적용; 내보내기·규칙 변경·판단 및 위험 수용은 별도 감사.
- 최초에는 작은 조직에 맞춰 역할 겸직을 허용할 수 있으나 **규칙 작성과 승인, 위험 수용 승인 권한은 분리**하는 방향으로 PoC를 검토한다.

### 3.2 대표 업무 흐름

- **등록→수집:** 자산 생성(시스템명, IP, OS, 담당자, 중요도, 외부 노출 정보/출처) → 호스트 키 확인·등록 → 테스트 접속 → 일정 설정 → 스캔 상태 확인.
- **새 이슈 조사:** 이슈 식별자·제품·버전 범위·출처 입력 → 최신 스냅샷으로 후보 도출 → 확인 불가/오래된 데이터 별도 표기 → 실행·노출·중요도 기준 정렬 → 담당자 판단 → 조치/재검증.
- **탐지 규칙 추가:** 초안 작성 → 형식/보안 정적 검증 → 지정 시험 서버 실행 → 증거·부하 확인 → 승인 → 규칙 버전 고정·전체 배포 → 이상 시 롤백.
- **수집 장애:** 실패 원인 분류 → 호스트 키 변경·인증 실패와 일시 네트워크 오류 구분 → 알림·재시도 정책 적용 → 담당자 조치 및 재수집.

### 5.2 프로세스·파일·권한·누락 처리

1. `rpm -qa`, `dpkg-query -W` 등 패키지 관리자를 우선 조회한다. 명령이 없으면 OS별 대체 경로를 사용한다. [원안 7쪽]
2. 실행 중 프로세스는 `ps` 및 접근 가능한 `/proc/<pid>/exe`를 이용해 조사한다. Tomcat은 `catalina.home` 등의 근거를 활용한다. root 전용 접근이 필요한 경우 해당 항목만 `확인 불가(권한 부족)`으로 남긴다.
3. 파일 탐색은 `/opt`, `/usr/local`, `/app`, 사용자 홈의 허용된 하위 경로처럼 수집기 정책으로 승인된 범위에서만 한다. `.nvm` 등 홈 경로는 담당자가 허용한 경우에 한한다. 심볼릭 링크·실제 경로 정규화·파일 개수·깊이 제한이 필요하다.
4. 대상에 지속적인 수집 프로그램/파일을 설치하지 않는다. 원격 세션·대상 OS 감사 로그는 남을 수 있으므로 '아무 기록도 남지 않음'으로 표현하지 않는다.
5. 파일 이름만으로 라이브러리 버전을 확정하지 않는다. 지원 범위에서 JAR 메타데이터(`pom.properties`, `MANIFEST.MF`) 및 중첩 아카이브를 확인하고 처리 불가 시 확인 불가로 기록한다. [S-11]
6. 수집 결과의 '미발견'은 *실제로 스캔한 범위에 한정*한다. 이전에 발견된 설치 인스턴스가 새 수집에서 보이지 않더라도 실패/권한/범위 변경이 있으면 자동 삭제 확정하지 않는다.

### 5.3 버전 비교 정책

- 비교는 문자열 사전순으로 하지 않는다. 예: `9.0.9 < 9.0.85`.
- 제품에 `version_scheme`을 명시한다. 예: `debian`, `rpm`, `semver`, `numeric`, `vendor_specific`, `unknown`.
- 원문 버전 `raw_version`은 절대 폐기하지 않는다. 비교가 어려운 제품은 비교 실패 원인을 저장한다.
- Red Hat 등 배포판의 백포트 패치 때문에 업스트림 버전만 보고 취약 확정하지 않는다. 배포판 릴리스 및 공급사 보안 권고 확인을 관리자 판단의 증거로 남긴다. [S-04, S-05]
- 범위 조건은 `<, <=, >, >=, =`, 포함·제외 구간을 지원하되 비교 체계가 다르면 `비교 불가`로 반환한다.
- 제품명/공급사 정규화는 사전 정의한 별칭을 사용하고 자동 병합 근거를 기록한다. PURL 등 표준 식별자는 적합한 패키지에 선택 적용한다. [S-12]

### 5.4 사용 및 노출 상태의 증거 모델

`installed_state`, `running_state`, `listening_endpoint`, `internal_reachability`, `internet_exposure`, `exposure_source`, `exposure_checked_at`을 분리한다. 인터넷 노출은 관리자 등록값·방화벽/NAT/LB 근거·권한 있는 외부 관측 등 별도 자료가 있어야 `확인됨`으로 표시한다. **포트 리스닝=인터넷 노출**이라는 자동 추론은 금지한다.

## 6. 탐지 규칙 DSL(데이터 형식)·안전성·승인

### 6.1 규칙 예시(정적 구조, 명령 문자열 없음)

```json
{
  "rule_id": "jar-log4j-core-filename",
  "version": 1,
  "category": "app_library",
  "product": "log4j-core",
  "find": {"kind": "file_pattern", "paths": ["/app", "/opt", "/usr/local"],
           "pattern": "log4j-core-*.jar"},
  "extract": {"source": "filename", "version_regex": "log4j-core-([0-9.]+)\\.jar"},
  "limits_profile": "standard"
}
```

위 JSON은 **설계 예시**이고 최종 JSON Schema는 3단계에서 승인한다. 실제 수집기 엔진은 제품 규칙과 무관하게 고정된 읽기 동작 목록만 제공한다. 새 엔진 기능·허용 경로 변경은 웹 관리자가 아니라 수집기 코드/설정 배포 변경으로 취급한다.

### 6.2 강제 안전 통제

| ID | 강제 요구사항 |
|---|---|
| SEC-R01 | 작업·규칙에 임의 셸/PowerShell 문장, 사용자 입력 명령행 인자 직결, URL 원격 실행을 허용하지 않는다. |
| SEC-R02 | `paths`는 정규화한 절대 경로만 허용하고 정책 외 경로·상위 경로 이동·심볼릭 링크 탈출을 차단한다. |
| SEC-R03 | 탐색 깊이·파일 수·읽기 용량·전체 실행 시간·출력 JSON 크기에 제한을 둔다. 구체 값은 PoC 후 확정한다. |
| SEC-R04 | 정규식은 안전한 기능 집합·복잡도 제한/시간 상한으로 ReDoS를 차단한다. [S-08] |
| SEC-R05 | 파일 내용은 버전 근거 범위만 읽고 인증정보·환경변수·비밀번호 파일을 규칙 대상에서 제외한다. |
| SEC-R06 | 규칙은 초안→검증→시험→별도 승인→활성→중지/롤백의 상태와 감사 이력을 가진다. |
| SEC-R07 | 규칙 실행 시 실제 적용한 `rule_version`, `engine_version`, `policy_version`, `limits_profile`을 관측에 남긴다. |

## 7. DB 작업 큐·수집기 운영 상태 머신

### 7.1 작업 계약

- **웹이 생성할 수 있는 작업 내용:** `asset_id`, `job_type`(basic/deep/verify), `priority`, 승인된 `rule_set_version`, 요청자, 요청 시각, 고유 요청 키. 명령어나 임의 경로 페이로드는 허용하지 않는다.
- **작업 상태:** `pending → running → success | failed | timeout | cancelled`; 재시도 가능 실패는 `retry_pending`을 거쳐 다시 `pending` 처리. `partial_success`는 작업 종료 결과 속성으로 표현한다.
- **수집기 선택:** 짧은 트랜잭션에서 `FOR UPDATE SKIP LOCKED`로 일정 개수 작업을 원자적으로 claim하고 DB 잠금을 해제한 뒤 원격 수집 수행. [S-03]
- **중복 방지:** 스케줄·요청키·자산·규칙셋 기준 중복 작업 제한; 스냅샷 저장에 멱등 키(`scan_run_id`) 부여.
- **유실 방지:** `worker_id`, `lease_until`, `heartbeat_at`, `attempt_count`, `last_error_code`, `next_retry_at` 관리. 워커 중단은 lease 만료 후 재할당한다.
- **재시도:** 네트워크 일시 오류는 제한 횟수·지수 백오프; 호스트 키 불일치/권한·인증 실패/정책 위반은 자동 반복 금지하고 담당자 확인 후 재수집.
- **정합성:** 스캔 관측·스냅샷 반영·작업 완료는 멱등성을 보장하고, 장애 시 중간 데이터가 최신 정상 상태를 덮어쓰지 않게 한다.
- **운영 제어:** 대상 호스트별 단일 작업, 전역·대역별·계정별 최대 동시 실행 수, 긴급 작업의 예약된 용량, 장시간 작업 중단·재개.

### 7.2 작업 분리 및 수집 스케줄

- **기본 수집:** OS·패키지·주요 프로세스·대표 버전·일반 리스닝 포트. 초기 일정은 '하루 1회 + 즉시 수집' 원안 유지.
- **심화 수집:** 광범위 경로, JAR/WAR/EAR 내부, npm/pip, 컨테이너 레이어 등 고비용 작업. 낮은 빈도 또는 조사 요청 시 실행.
- **긴급 영향 조사:** 기존 최신 결과로 우선 후보 검색 → 결과가 오래됐거나 확인 불가인 자산에 한정하여 우선 재수집. 인가되지 않은 무제한 즉시 수집 방지.
- **작업별 제한:** 연결·명령·호스트 단위 시간 상한, 출력 크기, 파일 탐색 한도를 분리해 설정하고 운영자가 조정할 수 있도록 한다. 추정 시간으로 고정하는 대신 테스트로 합격 범위를 정한다.

| `assessment_events` | assessment_id, previous_state, next_state, actor, reason, at | 판단·위험 수용·완료 변경 이력 |
| `audit_logs` | actor, action, object_type, object_id, at, source_ip, outcome | 중요 관리자 행위의 변경 불가 추적 |

### 8.2 데이터 품질 규칙

1. `asset_id`, `installation_id`, `run_id` 등 불변 내부 식별자를 사용하고 IP·호스트명 변경에 견딘다.
2. 설치 인스턴스의 동일성은 제품명만이 아니라 패키지 ID/실행 경로/설치 위치 같은 안정적인 식별자를 조합한다.
3. **원본 버전**과 **정규화/비교용 값**을 함께 저장한다. 파서 변경 후 과거 데이터의 해석이 달라질 수 있으므로 원본 보존이 중요하다.
4. `confidence`는 근거가 있는 분류(확인됨/추정)로만 사용한다. 임의의 정확도 확률을 만들어 표시하지 않는다.
5. 미발견·확인 불가·실패 상태에는 `reason_code`, `coverage_scope`를 남긴다.
6. 수집 결과가 실패하거나 부분 성공일 때 정상 최신 스냅샷을 무조건 덮어쓰지 않는다. 마지막 정상 관측일과 마지막 시도일을 분리한다.
7. 보존 기간은 최신 상태, 변경 이벤트, 제한된 원본 증거, 감사 로그의 4종류로 구분하여 결정한다. 오래된 결과는 보존 정책에 맞춰 축약/삭제한다.
8. 웹용 DB 계정·수집기 계정의 INSERT/UPDATE/SELECT 권한을 테이블 또는 전용 저장 프로시저 기준으로 최소화한다.

## 9. 보안·인증·위협 모델

### 9.1 자격증명과 네트워크

- 수집 전용 계정은 기본적으로 일반 계정이다. 일부 서버에서만 승인이 필요한 읽기 작업에 `sudo`를 허용할지 별도 심의한다(원안 미결정 유지).
- `authorized_keys`에는 `from="<수집기에서 보이는 고정 IP>"`, `no-pty`, `no-port-forwarding`, `no-agent-forwarding`, `no-X11-forwarding`을 적용한다. 예비 수집기 IP는 초기부터 등록 가능하도록 설계한다. NAT 시 실제 출발지 주소를 확인한다. [원안 12쪽]
- 위 옵션은 세션 기능 제한이며 일반 원격 명령을 자체적으로 무해하게 만들지는 못한다. 수집기에서 허용 동작만 생성하고 대상 계정 권한·파일 읽기 범위를 제한한다. [S-06]
- 키는 역할·네트워크 구역별 분리(최소 내부/외부 노출 서버), 0600 권한, 저장 볼륨 암호화, 관리자 접속 제한, 사용·교체 기록, 유출 대응 폐기 절차를 적용한다. SSH CA는 향후 검토로 남긴다.
- 호스트 키는 신뢰 가능한 별도 방법으로 초기 지문을 확인한다. 변경 시 자동 수락하지 않고 점검/재등록 승인을 요구한다.
- 수집기에는 수집 외 서비스 최소화, 관리용 SSH의 관리자 IP 제한, 정기 업데이트, 비밀 관리 및 관리자 인증 로깅을 적용한다. 수집기→대상 외의 네트워크 경로를 최소화한다.

### 9.2 공격 시나리오와 통제

| 위협 | 통제·실패 시 동작 |
|---|---|
| 웹 탈취 후 악성 작업·규칙 생성 | 역할 분리, 승인된 rule_set 참조, 엔진 고정 허용 동작·입력 검증·자원 한도; 거부 감사 |
| DB 계정 침해 | 웹/수집기 계정 최소 권한, 작업 스키마·상태 전이 검증, 변경 추적·백업 |
| SSH 개인키 유출 | 수집기 외 보관 금지, 내부/외부 키 분리, 출발 IP 제한, 폐기·일괄 교체 절차 |
| MITM/대상 교체 | 호스트 키 고정 검증, 변경 시 수집 중단·승인 절차 |
| 수집 결과 악성 입력 | JSON Schema/크기 제한·이상 문자 이스케이프·SQL 바인딩·XSS 출력 인코딩 |
| 악성 정규식/무한 파일 탐색 | 안전한 regex·허용 경로·symlink 통제·시간/파일 수/용량 제한 |
| 민감정보 로그 유출 | 명령행 토큰·환경변수·비밀번호 마스킹, 최소 원본 저장, 내보내기 RBAC |
| 작업 폭증/대상 과부하 | 전역·호스트별 병렬도, 작업 중복 제한, 심화 수집 분리, 요청률 제한 |
| 수집기 중단/DB 장애 | lease/heartbeat/재시도/멱등 저장, 마지막 정상 인벤토리 보전 |

### 9.3 웹·감사·백업·수용 조건

- 관리자 로그인 MFA, 세션 만료, 최소 권한, CSRF/XSS/SQL 인젝션 방어, API 입력 검증, 전송 구간 암호화, DB/백업 암호화.
- 자산 조회/내보내기·규칙 수정/승인·키 교체·위험 수용·사용자 권한 변경에 감사 이력을 남긴다. 감사 로그는 담당자가 임의 수정하기 어려운 보존 정책을 적용한다.
- 수집기 외 IP 사용, 비정상 시간대 SSH 접속, 연속 인증 실패, 호스트 키 변경, 규칙 대량 적용, 결과 급증 등에 경보 정책을 둔다.
- 장애 복구는 RPO/RTO 목표와 복구 시험 절차를 운영 정책으로 확정해야 한다. 복구한 수집기가 오래된 키·규칙·작업을 잘못 실행하지 않도록 검증한다.

## 10. Windows·네트워크 장비·컨테이너 확장 원칙

- **Windows(4단계):** WinRM 사용, 방화벽에서 수집기 출발 IP만 허용. 도메인 사용 시 Kerberos 우선 검토, 환경상 필요 시 NTLM 예외를 별도 승인한다. WinRM HTTPS 및 서버 인증서 검증 정책을 명확히 하고, 일반 사용자로 얻을 수 있는 결과와 관리자 권한 요구 항목을 구분한다. [S-09]
- **Windows 수집:** OS 빌드/핫픽스, 설치 프로그램(레지스트리 Uninstall), .NET, IIS 및 실제 실행 상태. 플랫폼 전용 파서를 사용하고 Linux POSIX sh 엔진에 임의로 결합하지 않는다.
- **네트워크 장비(4단계):** 벤더/OS 종류에 따른 `show version` 또는 안전한 조회 어댑터를 사용한다. 네트워크 장비 설정을 변경하는 명령은 비범위다. 지원 모델·권한·출력형식 테스트 목록을 운영한다.
- **컨테이너(5단계):** Docker/containerd/kubelet 정보 및 실행 이미지 태그를 수집 후보로 두되, 태그는 변경될 수 있으므로 가능하면 이미지 Digest도 보존한다. 컨테이너 내부 설치 패키지의 완전 탐지는 별도 기술검증 후 지원한다. [S-13]
- **라이브러리(5단계):** Java JAR/WAR/EAR 내 메타데이터·중첩 의존성, npm/pip 환경 등은 심화 수집. 직접 서버 전체를 수집하기 어려우면 승인된 SBOM 입력(별도 선택 기능)을 향후 고려할 수 있으나 기본 계획을 바꾸지 않는다.

## 12. 개발 단계·릴리스 게이트

원안의 **5단계 개발 구조는 유지**한다. 일정은 기술 스택·인원 확정 전 임의로 약속하지 않는다. 단, 원안 5단계에 있던 일부 운영·권한 보안 기능은 필수 안정성을 위해 앞당긴다.

| 단계 | 구현 범위 | 릴리스 통과 조건 |
|---|---|---|
| 1 기반 MVP | 자산/엑셀, 최초 SSH 설정·호스트 키, OS·패키지 수집, DB 큐, 기본 검색, 정기·즉시, 최소 권한·감사, 장애 복구의 최소 골격 | 일반 계정 PoC 통과, 결과 증거·확인 불가 분리, SSH 키/접속 검증, 작업 재시도·멱등성 |
| 2 탐지 확장 | 프로세스·경로 탐지, Tomcat/Node.js/Java 등, 다중 설치, 버전 비교기, 변경 이력, 설치/실행/노출 분리 | 서로 다른 두 버전 공존·권한 부족·백포트 사례에서 오탐/누락 설명 가능 |
| 3 규칙·판단·운영 | 규칙 웹 양식, 시험→승인→롤백, 조사 이슈·판단/조치 분리, 담당자·기한·보고서, 모니터링 | 규칙 보안·ReDoS·탐색 제한·RBAC 및 조치 이력 테스트 통과 |
| 4 플랫폼 확대 | Windows WinRM(설치/핫픽스/빌드), 네트워크 장비 벤더 어댑터 | 플랫폼별 인증/권한/원격 출력 오류 및 안전성 검증 |
| 5 심화 고도화 | JAR·npm·pip, 컨테이너/이미지 Digest, 선택적 위협 정보 오프라인 반입, 세부 알림·분석 개선 | 정밀 탐지 효과/자원 영향 합격, 기존 기본 수집 성능 회귀 없음 |

### 12.1 최초 PoC·성능 측정 순서

1. 대표 환경 선정: RHEL 계열·Ubuntu 계열, 서로 다른 패키지 관리자, 구버전 OS, 다중 JDK/Tomcat, `/opt` 사용자 설치, 권한 제한 서버.
2. 자체 제한 엔진과 Ansible 기능을 동일 서버에서 비교: 대상 Python 의존성, 접속·인증 요구, 원격 파일 잔존 여부, 패키지 식별률, 소요시간, 실패 처리, 규칙 통제. [S-02, S-10]
3. SSH 키 오·변경, NAT/출발 IP, 방화벽, 호스트 키 MITM 유사 시험, 연결 중단, 오래 걸리는 명령, 특수문자 결과를 검증.
4. 10/20/30 동시 실행 및 기본/심화 수집을 분리해 호스트 CPU·메모리·I/O·수집기 자원·DB 큐 적체를 측정.
5. 테스트 결과로 규칙 한도·수집 주기·동시성·보존 기간·인증 전략을 승인한다. 실패/미확인 범위를 '미지원'으로 명문화한 뒤 개발 범위를 동결한다.

**검색 예시:** `Tomcat < 9.0.86 AND 실행 중 AND 외부 노출=확인됨` 요청 시 비교 불가·노출 미확인 자산은 결과에서 조용히 누락하지 않고 **별도의 확인 필요 집계**로 제공한다. 실제 사용자가 설정한 버전 비교 체계에서만 `<`를 평가한다.

## 14. 관리자 판단 및 조치 워크플로

1. 보안 분석자가 이슈(CVE·공지 URL·영향 버전 조건·등록 시각)를 만든다.
2. 수집 스냅샷에서 인스턴스 후보를 조회한다. 최신성이 낮거나 확인 불가인 후보는 즉시 재수집 대상 표시.
3. 관리자가 영향 판단(`영향 가능`, `영향 없음`, `확인 필요`)을 **근거와 함께** 기록한다. 공급사 백포트/배포판 공지도 첨부 가능.
4. 조치 추적(`미조치`, `진행 중`, `완료`, `위험 수용`)을 별도 보존한다. 위험 수용에는 승인자·사유·기한을 요구한다.
5. 조치 후 재수집을 통해 실제 버전/패치 근거를 확인한다. 재확인 실패 시 자동 완료 금지.
6. 모든 상태 전이 및 사용자, 시간, 변경 사유를 감사 이벤트로 남긴다.

**가이드:** CVE 자동 매칭 결과는 **후보**이고, 확정 취약 판단은 관리자에게 있다. KEV/EPSS 등의 점수는 향후 우선순위 참고 자료이며 취약 판정을 자동 변경하지 않는다. [S-14, S-15, S-16]
